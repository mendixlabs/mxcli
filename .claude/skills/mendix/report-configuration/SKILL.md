# Configuration Report

`mxcli report configuration` answers "what does an environment have to be given?"
from the model alone. The real production values live in the deployment portal or
the pipeline; the report never reads them and says so on every page. Its job is the
list an administrator checks against, and the bugs no environment setting can fix.

## Run it

```bash
mxcli report configuration -p app.mpr -o docs/reports/configuration.html
mxcli report configuration -p app.mpr --format json -o docs/reports/configuration.json
# sign items off per environment, then re-render
mxcli report configuration --from docs/reports/configuration.json \
  --annotations docs/reports/configuration-annotations.yaml -o docs/reports/configuration.html
```

`mxcli report all` writes it with the other reports.

## Reading it

- **Checklist.** One row per thing an environment must supply:
  - a constant with no default or a placeholder (*must be set*);
  - a constant whose default points at localhost, a private address or a test host
    (*wrong unless overridden*);
  - a constant whose default looks like a secret (*set it and rotate the committed
    value* — the security report has the finding);
  - each scheduled event, to switch on or off;
  - each published service with authentication, whose callers need accounts.

  Sign rows off with `constant:<Name>`, `scheduled:<Name>`, `published:<Name>`,
  status `done` and a note naming the environment.
- **Fixed in the model** is what no environment can change: a REST client base URL
  or REST call location written as a literal URL to localhost, a private address or
  a test host, and a credential written as a literal. Fix these in the model — move
  the value to a constant — not in the portal.
- **"No use found in the model"** on a constant is not "unused": Java actions,
  JavaScript actions and widgets read constants the model does not show. Search the
  Java and JavaScript source before removing one.
- **What runs by itself** lists the scheduled events and the after-startup,
  before-shutdown and health-check microflows with what their call closure writes
  and calls out to. That is what a new environment does before anyone logs in — a
  startup flow that seeds demo data or calls a test host shows here.

## What it does not see

Consumed OData services, web-service calls and database connections take their
locations from settings the page does not read yet; web-service users and the
accounts a published service's callers need are created per environment and only
the services are listed. Ask whoever runs the environments for the rest.
